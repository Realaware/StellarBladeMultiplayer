Public upstream loader source at `e3ba1016562d6c0868c410d0a71e88bfcdbf691b` adds the following evidence:

- `UE4SS/src/UE4SSProgram.cpp`, `load_unreal_offsets_from_file`: reads `MemberVariableLayout.ini` from the working directory and applies parsed values through generated `MacroSetter.hpp`. The initialization path calls this loader before Unreal setup.
- `assets/MemberVarLayoutTemplates/MemberVariableLayout_4_26_Template.ini`: contains a `FUObjectArray` section with create/delete-listener fields. A template is not a Stellar Blade profile and does not establish the engine version.
- `UE4SS/include/Mod/CppUserModBase.hpp`: provides `on_ui_init`, `register_tab` and `register_keydown_event`; the UI-init comment identifies the loader's ImGui-context setup macro. These are candidate host interfaces for the existing panel. Their runtime/thread/teardown behavior on this game is unqualified.

HYPOTHESIS: current upstream's supported layout configuration may replace the old fork's hard-coded demo layout adjustment, allowing us to use an upstream loader and dependency without adopting the whole fork. This requires verifying the actual retail layout, configuration consumers and loader behavior. The mere presence of configuration fields does not prove that every initialization path uses them, or that all other Stellar Blade fixes are unnecessary.

Local inspection of the pinned official source now confirms that `src/UObjectArray.cpp` listener add/remove operations call these generated accessors. `generated_include/MemberVariableLayout_SrcWrapper_FUObjectArray.hpp` obtains each field offset from `MemberOffsets` and caches it in a function-local static; any verified overrides must therefore be established before the first accessor call. These source paths replace the corresponding old direct listener-member accesses; they still do not supply verified Stellar Blade offsets.

`src/UnrealInitializer.cpp` records its game-thread ID in `HookedEngineTick`, registered as an engine-tick pre-callback. Its getters reject or return an empty ID before initialization. The ID and readiness globals are not atomic in this source. A future adapter must qualify the actual hook/thread and synchronization/lifetime boundary; UI/worker calls to these getters alone cannot establish a verified game-thread entry point.

Candidate source pair: upstream loader `e3ba1016562d6c0868c410d0a71e88bfcdbf691b` with Unreal submodule `38e7171e9e8c4a871ff84765848f0290ca34a44e`. This pair is pinned for inspection only; it is not selected as a supported runtime ABI. The installed fork remains preserved. Its headers and the new upstream headers must not be mixed.

The source/toolchain/dependency/output fingerprints are recorded in [upstream-build-profile.json](upstream-build-profile.json). Build scripts were reviewed and dependency licenses/source are retained in ignored output. This candidate's supported runtime ABI is still unqualified. No new game DLL target may assume compatibility with the installed fork.

The first isolated game run confirmed loader routing, then failed the required object-array scan and timed out. The console-manager ambiguity is optional and unused in this source pin. See [First upstream startup](upstream-startup-01.md) for settings, failure, post-exit preservation checks and static hypotheses. [Array static evidence](upstream-array-static.md) shows why cache-disabled startup still requires the exact listener layout; [startup bounds](upstream-startup-bounds.md) identifies later waits not bounded by the scan timer. Resolve those findings before another runtime experiment, then observe main-menu initialization and clean teardown and qualify UI callback/thread ownership before hosting the panel. Initial UI must leave native creation/admission disabled. Ten clean starts/exits and unload behavior remain required. Do not copy demo offsets into a retail configuration as a shortcut.

After lifecycle qualification, a read-only game-thread experiment must identify native inventory, actual loaded slot and persistent instance identity across reloads and slot recreation. Only then implement the save adapter and the Create button's native operation with disposable slots, preservation/persistence receipts and recovery tests. The existing `RuntimeController`, panel and backup verifier are the consumers; synthetic identities or filesystem filenames cannot replace these native findings.
